## 小组人机协作范式总结

本项目稳定采用「**先限定、再推导、必核验、后采用**」的五步范式：

1. **先限定问题与符号**：开工前由 A 锁定研究问题、假设、符号与得分/阈值方向，避免后续反复漂移。
2. **模型只出草稿**：让模型提供推导草稿、代码骨架、图表脚本与文献要点，明确**不得代下结论**。
3. **用可复查动作核验**：手算特例（如 KDE 手算 0.5558）、断言（分数方向、混淆矩阵自洽）、独立实现重跑（C 的 50 项对账 0 偏差）、脚本核验（32 项数字复核）——不写「已审核」这种空话。
4. **如实记录错误并修正**：A 侧设计被 C 证伪（球壳边界标签矛盾、鞍部紧凑簇非空区）、配置口径被纠正（H4 不得把测试最优当选择准则）、版本口径被修正（far-only 冻结 vs near post-hoc）——全部保留证据链。
5. **最后人工决定采用或拒绝**：每份记录都有「最终采用」栏，说明采用、改写或拒绝及理由。

**分工与互审闭环**：A 审 B（数据协议）→ B 审 C（实现与复现）→ C 审 D（论文图表与数字）→ D 审 A（理论与文献）；四人各主责一块、各审一块，核心推导、实验协议、实现与结论均有独立检查人。

## 回合 4：不采信库输出，另写一份实现独立重算

| 字段 | 内容 |
|---|---|

## 回合 5：发现并修正设计错误 ① —— 2.5σ 球壳异常在几何上不成立

| 字段 | 内容 |
|---|---|
| 会话序号 / 时间 | 回合 5 / 2026-11-27 |
| 当前任务 | 设计 H3（局部 vs 全局）需要的「局部/边界异常」 |
| 提示词 | 承接回合 2 的协议制定；模型初稿把「局部异常」定义为稀疏簇周围 **2.5σ 球壳** |
| 模型输出 | 「theta ~ Uniform(0,2π)；X = (2,0) + 2.5·[cosθ, sinθ]」，并称该构造可用于检验局部方法相对全局方法的优势 |
| 人工检查 | **解析推导，不跑任何样本**：稀疏簇每维 sd=1.0，二维标准高斯径向满足 `P(r≥ρ)=exp(−ρ²/2)`。代入 ρ=2.5 得 `P = e^{−3.125} = 4.39%`，即 500 个**正常**稀疏簇点里约有 **22 个**落在球壳之外。这些正常点比被标注为「异常」的球壳点更稀疏、密度更低、异常分数更高 —— **标签与得分自相矛盾**，任何检测器都不可能在该子集上取得合理召回。进一步算 ρ=4.0 时 `P=3.36e−04`（约 0.17 个）可消除矛盾，但 r=4 处已与远端异常环 r∈[5,7] 重叠，不再构成独立的「局部」类型 |
| 证据与判断 | **模型输出错误**：球壳式「局部异常」在本 DGP 下不成立。判断依据为纯解析结果，未运行任何样本 |
| 修正交互 | 要求改设计：把 `near` 类型改为「空区中的紧凑小簇」，`X = (0,5) + 0.35·Z`，并把上述推导写进协议 §3.2 与 §12 变更记录，明确标注「改动前未接触任何测试集结果，纯解析推导得出」 |
| 最终采用 | 采用新构造（`type_id="compact_void"`，默认 `enabled=false`），并把旧球壳的证伪过程原样留档 |

## 我稳定使用的协作范式（B 版）

1. **先锁约束，再要产出。** 任何「帮我写协议」的请求之前，先把样本量、网格、阈值规则、得分方向固定下来，并明确「这些值在跑实验之前锁死，跑完不许回改」。模型的产出只填数值，不许改结构。
2. **凡是模型给的数，要求它给出可手算的推导链。** 参考带宽、超阈个数、`P(r≥ρ)` 都要求给出中间量，然后用计算器/纸笔独立复算一遍。三次核对里有一次就抓到了网格缺欠平滑端点（回合 2）。
3. **不采信「库跑通了」当正确性证据。** 要求另写一份实现（手写 KDE、手写 LOF、手算 AUC/AP），与库输出逐位对账。手写 LOF 与 sklearn 偏差 0.0 这个结果，比任何「我检查过了」都更有说服力。
4. **设计类结论必须实测，不能只推理。** 回合 5 靠解析推出「球壳不可用」；回合 6 我犯的错恰恰是**只推理没实测** —— 忽略了 `novelty=True` 的语义差异。此后的规矩是：任何涉及「某构造能/不能区分两个方法」的论断，一律先写纯坐标探针实测，再下结论。
5. **被推翻就撤回，并留痕。** 回合 6 把自己上一轮的结论写进协议 §3.2.1 并标注「已证伪」，回合 7 把 C 的报错原文与我的缺陷一并留档。**不删、不改写成「一次就对」。**
6. **锁定文件受约束，说明性更正走旁路。** `config_ref.json` 禁止同版本改字段，所以本轮对 `near.design_note` 的更正**不写进 JSON**，而是在协议 §3.2.1 明确「以本节为准，字段更正留到 B-v1.1 一并处理」。

## 6. 我如何与AI协作的（不是“让 AI 写作业”，是“把 AI 当被测对象”）

1. **先钉不可协商的量，再让模型动手**。网格、默认参数、阈值方法、得分方向全部写成 `protocol.load_config()` 的断言——配置一漂移就当场抛错，不靠我记。
2. **让「正确」有第二个来源**。手写实现 × 库实现 × 队友的参考实现三方交叉；任何两方偏差都能定位是公式、符号还是版本问题。
3. **证据要做成可执行脚本，而不是写在文档里**。「已验证」必须由退出码 + 实测量支撑（阈值、超阈数、`max|Δ|`），不接受只回 PASS。
4. **优先防「静默失效」**。回合 1 的教训：脚本崩了但旧结果还在，审计照样 PASS。所以每个脚本都打印实测量，审计脚本自己带「与另一处记录一致」的检查项。
5. **越权动作先停**。协议权、签字权不在我手上时，我只出待签件 + 影响清单，把别人的决策成本压到最低；发现自己上一条指令越权，就主动撤回（回合 5）。
6. **先预测、再实测、再解释偏差**。每轮先写「我认为会怎样、为什么」，跑完逐行对照。发现了 C18 的随机流错误和 AUC 的分母错误——**预测表不是为了好看，是为了让错误显形**。
